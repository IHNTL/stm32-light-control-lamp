# 串口通信协议

- 波特率：115200，8 位数据位，1 位停止位，无校验（8-N-1）
- 编码：ASCII 文本行，便于在串口助手里直接手敲调试
- 行结束符：`\n`（`\r` 会被忽略，所以 CRLF 和 LF 都能用）
- 命令大小写不敏感，MCU 内部统一转成大写处理
- 单行最大 48 字符，超长整行丢弃

## 一、PC → MCU

| 命令 | 参数 | 说明 |
|---|---|---|
| `LIGHT <0-100>` | 亮度百分比 | 设定亮度，**同时切换到 PC 控制模式** |
| `MODE AUTO` | — | 切到自动光控模式 |
| `MODE PC` | — | 切到 PC 控制模式 |
| `QUERY` | — | 查询当前状态 |
| `HELP` | — | 列出所有命令 |

命令与参数之间可以用空格或逗号分隔，例如 `LIGHT 60`、`LIGHT,60` 都合法。

## 二、MCU → PC

### 周期性上报（200 ms 一次）

```
DATA adc=1873 duty=42 target=42 mode=AUTO
```

| 字段 | 含义 |
|---|---|
| `adc` | 光敏 ADC 原始值，0 ~ 4095（8 次采样的平均值） |
| `duty` | 当前实际输出占空比，0 ~ 100 |
| `target` | 渐变目标占空比，0 ~ 100 |
| `mode` | `AUTO` 或 `PC` |

> `duty` 和 `target` 在渐变过程中会不一样 —— 前者是灯当前的实际亮度，后者是它正在靠近的目标。

### 命令响应

| 回复 | 场景 |
|---|---|
| `OK,LIGHT=60` | 亮度设置成功 |
| `OK,MODE=AUTO` / `OK,MODE=PC` | 模式切换成功 |
| `MODE,AUTO` / `MODE,PC` | 模式真正发生变化时主动通知 |
| `ERR,LIGHT needs a value 0-100` | 参数缺失 |
| `ERR,MODE needs AUTO or PC` | 参数非法 |
| `ERR,unknown command XXX` | 未知命令 |
| `EVT,pc timeout` | PC 控制模式下超时，已自动切回自动模式 |

### 开机输出

```
Light Control Lamp ready
Type HELP for the command list
MODE,AUTO
```

## 三、典型使用流程

```text
PC:  MODE PC              MCU: MODE,PC          <- 模式变化，主动通知
                          MCU: OK,MODE=PC       <- 对本次命令的应答
PC:  LIGHT 80             MCU: OK,LIGHT=80
MCU: DATA adc=1500 duty=80 target=80 mode=PC
PC:  QUERY                MCU: DATA adc=1500 duty=80 target=80 mode=PC
PC:  MODE AUTO            MCU: MODE,AUTO
                          MCU: OK,MODE=AUTO

（若 3 秒不发任何指令）
MCU: EVT,pc timeout
MCU: MODE,AUTO
```

> 注意顺序：**"主动通知"先于"命令应答"**。因为 `App_SetMode()` 在
> `App_HandleCommand()` 发出 `OK,...` 之前就已经完成了模式切换并推送通知。
> 只写 `MODE AUTO`（已是 AUTO 模式）时不会重复通知，只会收到一行 `OK,MODE=AUTO`。

## 四、实现要点

- 接收在 `USART1_IRQHandler` 里逐字节写入环形缓冲，**中断里不做任何解析**
- `Serial_Poll()` 在主循环里把字节拼成整行，拼好才返回 1
- 收到任何合法命令都会刷新超时计时器，`LIGHT` 命令会顺带切到 PC 模式
- 上报走阻塞发送。当前数据量很小（每 200 ms 约 40 字节），不会影响其他任务；
  将来若上报量变大，应改为 DMA 发送

## 五、协议为什么这样设计

这一节记录每一条设计取舍的理由，以及**被否掉的方案**。

### 5.1 为什么是 ASCII 文本行，不是二进制帧

| 方案 | 优点 | 为什么没选 |
|---|---|---|
| **ASCII 文本行**（采用） | 串口助手里能手敲调试；出错肉眼可见；无需写上位机 | 体积效率低 —— 但本项目每 200 ms 才 40 字节，带宽完全不是瓶颈 |
| 二进制帧（帧头 + 长度 + 载荷 + CRC） | 紧凑、抗干扰、适合传大数据 | 调试必须写解析脚本，出错了只能对着十六进制猜 |
| 单字符命令（`A` / `B` / `C`） | 最简单、省带宽 | 没有可读性，命令一多就记不住；无法携带参数 |

**判据**：本项目是"**人机交互**"场景（有人手敲），不是"机机交互"。协议的可读性 >> 传输效率。
如果以后要传 ADC 波形（每秒上万点），那才需要为数据流单独设计一条二进制通道，跟命令通道并存。

### 5.2 三层的职责边界

这是整个串口模块最重要的结构，**每一层只做一件事**：

| 层 | 代码位置 | 只做什么 | 绝不做什么 |
|---|---|---|---|
| 字节搬运 | `USART1_IRQHandler` | 取字节、写环形缓冲 | **不解析、不判断、不回复** |
| 行组装 | `Serial_Poll()` | 把字节拼成整行，遇 `\n` 返回 1 | 不认识任何命令词 |
| 命令分派 | `App_HandleCommand()` | 切词、比对命令表、执行、回复 | 不碰任何硬件寄存器 |

**为什么中断里绝不解析？** 中断服务函数里每多花一微秒，主循环就被推迟一微秒。更危险的是：
如果在中断里调用一个可能阻塞的函数（比如带 `while` 等待的发送），中断会被拖住，紧接着
**下一个字节就丢了** —— 而且这种丢包现象随机出现，极难复现。所以中断只做"搬"这一件确定的事。

**中间为什么要多一层"行组装"？** 因为"一个命令"和"一个字节"不是一回事。底层给的是离散字节，
上层需要的是完整一行。行组装层就是这两者之间的适配器，它让上下两层可以各自独立地改：
比如把终止符从 `\n` 改成 `;`，只需要动 `Serial_Poll()` 一个函数。

### 5.3 分隔符为什么允许空格**和**逗号

`strtok(pLine, " ,")` —— 分隔符集合里同时放了空格和逗号，于是下面三种写法完全等价：

```
LIGHT 60      LIGHT,60      LIGHT ， 60
```

**代价**是几乎为零（`strtok` 多接受一个字符），**收益**是用户记住了"用逗号分隔"还是"用空格分隔"
都不会出错。这是典型的"**宽容输入、严格输出**"原则 —— 输入端尽量容忍人的随意，
输出端（`OK,` / `ERR,`）则固定格式，便于程序解析。

### 5.4 回复前缀即语义分类

所有输出都带一个大写前缀，PC 端拿到一行后**看前缀就能决定怎么处理**，不需要解析全文：

| 前缀 | 含义 | 例子 | PC 端建议处理 |
|---|---|---|---|
| `OK,` | 命令执行成功 | `OK,LIGHT=60` | 确认操作，可忽略 |
| `ERR,` | 命令有误 | `ERR,MODE needs AUTO or PC` | 提示用户改正 |
| `DATA ` | 周期性状态上报 | `DATA adc=1873 duty=42 ...` | 更新界面 / 画曲线 |
| `EVT,` | 非请求的事件通知 | `EVT,pc timeout` | 弹提示、切回手动 |
| `MODE,` | 模式变化的主动通知 | `MODE,AUTO` | 同步界面上的模式指示 |

> `DATA` 后面用的是**空格**而不是逗号，是为了把"首字段是值"和"首字段是类型"区分开 ——
> `DATA adc=1873` 的第一段 `adc=1873` 是键值对，而 `OK,LIGHT=60` 的第一段是状态词。

### 5.5 四个容易忽略的设计点

**① 应答里回显数值。** `OK,LIGHT=60` 而不是光一个 `OK`。因为上层可能对参数做过钳位
（发 `LIGHT 200` 会收到 `OK,LIGHT=100`），回显实际生效的值，用户立刻知道被限制到了多少。

**② 模式变化单独通知。** 除了命令应答，模式真正改变时还会主动推一行 `MODE,AUTO`。
这样 PC 端不必轮询，也**能在看门狗自动切回 AUTO 时立刻获知**（配合 `EVT,pc timeout`）。

**③ 副作用写进命令语义里。** `LIGHT` 命令**顺带切到 PC 模式** —— 这是个显式副作用，
写进了命令表和文档。理由：用户既然要远程设亮度，显然不希望下一秒被光敏数据覆盖掉。
如果做成"必须显式先发 MODE PC"，多一步操作、更容易踩坑。

**④ 看门狗对任何一行都喂。** `s_lastCommandTick` 在切词之后、比对命令之前就更新，
所以**连打错的命令也会刷新超时计时器**。这是刻意的：只要能收到完整的一行，
就说明 PC 端和链路都还活着 —— 该被保护的场景是"**对方掉线了**"，而不是"对方打错字了"。

### 5.6 边界防御清单

协议层能承受的错误输入，以及各自的处理方式：

| 异常输入 | 处理 | 位置 |
|---|---|---|
| 只发 `\r\n`（空行） | 忽略，不触发任何命令 | `Serial_Poll()`，`s_lineLength > 0` 才返回 1 |
| 一行超过 48 字符 | **整行丢弃**（不是截断） | `Serial_Poll()`，`s_lineLength = 0` |
| 环形缓冲写满（容量 64 B，可用 63 B） | 静默丢弃新字节，不覆盖旧数据 | `Serial_RxPush()`，`next != tail` 才写入 |
| 参数越界（`LIGHT 200`） | 钳位到 100，并回显生效值 | `App_HandleCommand()` |
| 参数不是数字（`LIGHT abc`） | `atoi` 返回 0 → 按 0 处理 | 同上 |
| 缺参数（`LIGHT`） | `ERR,LIGHT needs a value 0-100` | 同上 |
| 未知命令（`FOO`） | `ERR,unknown command FOO`，**回显原词** | 同上 |
| 串口溢出错误（ORE） | 读一次 `DR` 清除，否则中断会一直反复进 | `USART1_IRQHandler()` |

> 超长行为什么"整行丢弃"而不是"截断"？截断会得到半条命令（比如 `LIGHT 6` 从 `LIGHT 600000` 里截出来），
> 执行结果是错的却看起来合法 —— **静默的错误比显式的失败更危险**。

### 5.7 已知局限

- **发送是阻塞的。** `Serial_SendByte()` 靠 `while (TXE == RESET)` 等待。当前每 200 ms 约 40 字节，
  115200 下耗时不到 4 ms，影响可忽略。若上报频率或数据量上升，应改为 **DMA 发送**。
- **没有校验和与重传。** 串口在短距离、低波特率下误码率极低，且本项目每次上报都是最新状态，
  丢一帧下一帧就补上了，重传机制只会让协议变复杂而无收益。
- **单行最大 48 字符**是硬限制。若要传输更长的内容（比如配置字符串），需要重新设计。
