1 · 选外设的四步法这不是玄学，是一套可重复执行的流程

初学者最容易犯的错是"看到教程用 PA1 就抄 PA1"。正确做法是走下面四步 —— 每一步都能落到纸面上：

① 需求 → 信号类型

问自己：我要的是模拟量、频率/占空比可调的方波、还是串行数据流？

答案直接锁定外设类别：模拟量 → ADC；方波 → 定时器比较输出；串行 → USART/SPI/I2C。

② 查资源地图

翻数据手册的引脚定义表和参考手册的外设章节，列出这个型号到底有几个、各自挂在哪条总线、有哪些通道、默认映射在哪个引脚。

F103C8T6 是 48 脚小容量型号，外设数量比大容量型号少，可选项本来就不多。

③ 划掉"不可动"的引脚

先排除，再挑选。固定不可动的有：

  • PA13 / PA14 → SWD 调试口，改成普通 IO 会导致芯片锁死
  • PD0 / PD1 → 8 MHz 晶振
  • NRST / BOOT0 / VBAT
  • PC13 → 板上已经焊了 LED
  • PA15 / PB3 / PB4 → 默认被 JTAG 占用，要用得先关 JTAG

④ 建"占用登记表"防冲突

每确定一个外设，就登记 外设名 + 引脚 + 归属模块。新模块开工前先查表，撞了就换。

这套登记的最终形态就是第 9 节那张表 —— 它同时也是原工程出事的根因：没有人维护这张表。

第 ④ 步为什么最重要 原工程 4 个致命冲突，全都源于同一个失误：两个模块各自独立地"挑了一个方便的外设"，谁也不知道对方也在用。Timer.c 挑了 TIM2，PWM.c 也挑了 TIM2；LED.c 挑了 PA1/PA2，PWM.c 也要 PA1。代码单独看都没问题，合起来必然崩。

2 · 定时器怎么选PWM 给了 TIM2，系统节拍给了 TIM3 —— 这是怎么定的

2.1 先看 F103C8T6 手上有几个定时器

定时器类型挂在哪条总线计数位宽可用通道与默认引脚本项目去向
TIM1高级APB2（72 MHz）16 位 CH1→PA8 · CH2→PA9 · CH3→PA10 · CH4→PA11 空闲 但没有引脚可用（PA9/10 给了串口）
TIM2通用APB1（36 MHz，倍频后 72 MHz）16 位 CH1→PA0 · CH2→PA1 · CH3→PA2 · CH4→PA3　（重映射后还可用 PA15/PB3/PB10/PB11） PWM 输出
TIM3通用APB116 位 CH1→PA6 · CH2→PA7 · CH3→PB0 · CH4→PB1　（重映射后 PB4/PB5/PB0/PB1） 1 ms 系统节拍
TIM4通用APB116 位 CH1→PB6 · CH2→PB7 · CH3→PB8 · CH4→PB9 空闲（PB6/PB7 给了 OLED）
SysTick内核—24 位递减 无输出引脚，只能产生中断 被 Delay 用
一个容易忽略的点：APB1 上的定时器时钟其实是 72 MHz TIM2/3/4 挂在 APB1（最高 36 MHz），但 STM32 有个规则：当 APB 预分频系数不为 1 时，定时器时钟自动倍频 ×2。所以 TimxCLK = 36 × 2 = 72 MHz，和系统时钟一样。这就是为什么 PSC 写 72 就能得到 1 MHz 计数 —— 不是 36/72。

2.2 决策一：PWM 为什么落在 TIM2

要一路可调占空比的方波，TIM1~TIM4 都能做，为什么选 TIM2？ 顺便定下：占空比分辨率 1000 级，频率 1 kHz
▶

筛选过程是排除法，一步步缩到只有一个答案：

  1. TIM1 出局：它的 CH2/CH3 默认在 PA9/PA10 —— 那正是我要留给串口的两个脚。要用 TIM1 就得开重映射或换脚，白白增加复杂度。
  2. TIM3 出局：我打算让它做系统节拍（下面 2.3 会讲为什么），一个定时器同时干"定时中断"和"输出波形"两件事，配置会互相干扰，调试时很难分清是谁的问题。
  3. TIM4 出局：CH1/CH2 在 PB6/PB7 —— 已经给了 OLED 的软件 I2C。CH3/CH4 在 PB8/PB9 倒还空着，但那就得换个引脚、换个通道，没有额外收益。
  4. TIM2 胜出：CH2 的默认引脚就是 PA1，不需要重映射；PA1 紧挨着 PA0（光敏），接线时两块模块可以挨着插，飞线短、看着不乱。
结论：TIM2_CH2 → PA1。理由排序是 ①引脚现成不冲突 → ②与节拍定时器分离 → ③布线集中，而不是"教程都这么写"。
反过来说：如果当时选了 TIM3 出 PWM 那就得用 PA6/PA7 或 PB0/PB1。PA6/PA7 虽然空着，但意味着节拍要改用 TIM2 或 TIM4，两个定时器的"职责"整体错位 —— 改一次要动两个模块的代码。尽早在纸上定死"谁干什么"，能省掉后面这种连锁修改。

2.3 决策二：系统节拍为什么用 TIM3，而不是 SysTick

产生"每毫秒加一"的心跳，最简单的是 SysTick，为什么改用 TIM3？ 这个决定直接影响了整个程序能不能"不阻塞"
▶

先厘清节拍是干什么的。程序里到处需要"每隔 N 毫秒做一次"：渐变 10 ms、上报 200 ms、刷屏 500 ms、心跳 500 ms。要做到这些，必须有一个能回答"现在过了多久"的时钟源。

三个候选方案对比

方案优点致命问题
delay_ms() 空转 最好懂 阻塞。等 500 ms 期间串口一个字节都收不到、OLED 不刷新、看门狗不喂 —— 原工程就栽在这
SysTick 内核自带，不占外设 标准库的 Delay.c 已经在用它做微秒/毫秒延时。两处都用会造成重新配置时延基准被改写，而且 SysTick 中断优先级最低，容易被别的中断推迟，计时不准
TIM3 独立中断 与 Delay 完全隔离；中断优先级可自由设定（本项目设抢占 2）；以后要改成"1 kHz 触发 ADC 采样"也顺手 占用一个通用定时器（本来就空着）
结论：用 TIM3 产生 1 ms 中断。判据是"不与已有功能共享资源" —— 既然 SysTick 已经被延时函数占了，就不要再挤进去。

实现只要两个东西：一个中断里自增的计数器，和一个判断"时间到没到"的函数。后者是整个非阻塞架构的关键，注意它不用减法以外的任何运算：

System/Timer.c节拍与非阻塞周期判断
static volatile uint32_t s_tickMs = 0;

void TIM3_IRQHandler(void)
{
    if (TIM_GetITStatus(TIM3, TIM_IT_Update) == SET)
    {
        s_tickMs++;
        TIM_ClearITPendingBit(TIM3, TIM_IT_Update);
    }
}

/* 到点返回 1，并把参考点前移；用无符号减法，计数器溢出也能正确工作 */
uint8_t Timer_IsElapsed(uint32_t *pLast, uint32_t interval)
{
    uint32_t now = s_tickMs;

    if ((now - *pLast) >= interval)
    {
        *pLast = now;
        return 1;
    }
    return 0;
}
这里有个容易写错的地方 不要写成 if (now >= *pLast + interval)。当 s_tickMs 累加到 0xFFFFFFFF 翻转回 0 时，*pLast + interval 会溢出，判断永久失效。now - *pLast 这种无符号相减的写法即使跨越翻转点也能算出正确的差值（约 49.7 天才翻一次，但正确写法不花额外代价，没有理由不写对）。

2.4 决策三：PWM 频率和分辨率怎么定

为什么是 1 kHz / 1000 级，而不是 20 kHz / 100 级？ 频率和分辨率是一对相互制约的参数
▶

核心矛盾：定时器计数器时钟固定为 1 MHz 时，频率 × 级数 = 1 MHz 是个恒等式。想要高频就得牺牲分辨率，想要细分辨率就得降低频率。

方案频率级数人眼观感调光手感
粗10 kHz100不闪每一步跳 1%，暗部变化突兀
本项目1 kHz1000不闪（远高于 200 Hz 临界）0.1% 一步，渐变丝滑
细100 Hz10000能看到闪烁极细，但人眼先受不了
结论：1 kHz / 1000 级。判据是 ①频率必须远高于人眼闪烁临界（约 200 Hz）→ ②在满足①的前提下把分辨率拉到最大。

另外 1000 这个数字还有个工程上的好处：占空比百分比和寄存器值可以一一对应，不需要浮点运算。

System/PWM.h用宏把百分比换算藏起来
#define PWM_PERIOD              1000    /* 1 kHz, 1000 duty steps */
#define PWM_PERCENT_TO_DUTY(p)  ((uint16_t)((p) * (PWM_PERIOD / 100)))

/* 上层的代码永远只跟"百分比"打交道： */
PWM_SetDuty(PWM_PERCENT_TO_DUTY(42));   /* -> 420 */

2.5 PWM 初始化代码逐行读

System/PWM.cTIM2_CH2 → PA1
void PWM_Init(void)
{
    /* ① 开时钟：TIM2 在 APB1，GPIOA 在 APB2 —— 两条总线的开关是分开的 */
    RCC_APB1PeriphClockCmd(RCC_APB1Periph_TIM2, ENABLE);
    RCC_APB2PeriphClockCmd(RCC_APB2Periph_GPIOA, ENABLE);

    /* ② 引脚配成"复用推挽输出"——这是关键，配成普通推挽就只是普通 IO，
          定时器根本控制不到这个脚。原工程 LED.c 就是错在这里 */
    GPIO_InitStructure.GPIO_Mode  = GPIO_Mode_AF_PP;
    GPIO_InitStructure.GPIO_Pin   = GPIO_Pin_1;
    GPIO_InitStructure.GPIO_Speed = GPIO_Speed_50MHz;
    GPIO_Init(GPIOA, &GPIO_InitStructure);

    /* ③ 时基：72 MHz / 72 = 1 MHz 计数，计满 1000 个就是 1 kHz */
    TIM_TimeBaseInitStruct.TIM_Prescaler = 72 - 1;   /* 寄存器写 71，实际分频 72 */
    TIM_TimeBaseInitStruct.TIM_Period    = PWM_PERIOD - 1; /* 寄存器写 999，实际周期 1000 */
    TIM_TimeBaseInitStruct.TIM_CounterMode = TIM_CounterMode_Up;
    TIM_TimeBaseInit(TIM2, &TIM_TimeBaseInitStruct);

    /* ④ 输出比较通道 2：PWM1 模式 = 计数值 < CCR 时输出高电平 */
    TIM_OCInitStruct.TIM_OCMode      = TIM_OCMode_PWM1;
    TIM_OCInitStruct.TIM_OCPolarity  = TIM_OCPolarity_High;
    TIM_OCInitStruct.TIM_OutputState = TIM_OutputState_Enable;
    TIM_OCInitStruct.TIM_Pulse       = 0;              /* 初始占空比 0 = 不亮 */
    TIM_OC2Init(TIM2, &TIM_OCInitStruct);            /* 注意是 OC2，对应 CH2 */

    TIM_Cmd(TIM2, ENABLE);
}
TIM_Prescaler = 72 - 1 里的减一是怎么回事 寄存器存的是"分频系数减一"。写 71 → 实际分频 72。同理 TIM_Period = 999 → 实际计 1000 个数。所以看到别人的代码里到处是 -1，不是随手写的。忘掉这个减一，频率就会差一点点：71 分频 → 1.014 kHz，不致命但说明没搞懂。

3 · ADC 通道怎么选为什么是 ADC1_IN0（PA0），采样时间为什么必须调大

3.1 通道和引脚是焊死的

ADC 的通道号不是你想选就能选，它和引脚是一一对应的硬件连线关系。F103 的映射是固定的：

通道对应引脚本项目状态通道对应引脚本项目状态
IN0PA0光敏 AOIN8PB0空闲
IN1PA1被 PWM 占IN9PB1按键预留
IN2PA2空闲IN10~15PC0~PC5空闲
IN3PA3空闲IN16内部温度传感器未用
IN4~7PA4~PA7空闲IN17内部 Vrefint未用
PA2、PA3、PA4 都空着，为什么光敏非要用 PA0？ 答案很朴素：因为 PWM 先占了 PA1，而 ADC 用 PA0 不需要动任何配置
▶
  • PA0 → IN0：通道号和引脚序号正好对齐，ADC_Channel_0 配 GPIO_Pin_0，两者读起来一致，不容易写错。
  • 为什么不用 PA2（IN2）：能用，但没理由。PA0 与 PA1 相邻，光敏模块和 LED 可以并排插在板子同一侧，走线短。
  • 为什么不用 PA4~PA7（IN4~IN7）：这几脚虽然空着，但它们同时是 SPI1 的 NSS/SCK/MISO/MOSI。留着的价值比用一个 ADC 通道大 —— 万一以后要加 SPI 屏幕或 Flash，就不用重新挪线。
结论：ADC1 的 IN0 → PA0。判据是"不需要重映射、不需要额外配置、与已占资源不冲突"，三个条件同时满足的首选就是 PA0。
注意这里没有"最优解"，只有"当前约束下的合理解" 如果当初 PWM 选了 PA3，光敏大概率就会用 PA2。引脚分配是决策顺序决定的：先定输出（引脚约束最强的），再定输入（最灵活的）。这次恰好反过来 —— 光敏先定，PWM 跟着挪，才有了 PA1 的取舍。

3.2 为什么必须配合 DMA

配置成连续转换模式后，ADC 一启动就自己不停地转，每转完一次把结果丢进 ADC1->DR。这里有个陷阱：如果你不读走 DR，下一次转换就会把它覆盖掉，同时置位 ORE 溢出标志。

最笨的办法是在主循环里不停查 EOC 标志然后读 —— 那样 CPU 就被绑死在"守着 ADC"这件事上。DMA 的作用就是把这件机械劳动交给硬件：每次 EOC 自动把 DR 搬到内存数组里，搬满 8 个就自动绕回开头（循环模式），CPU 完全不用管。

DMA1_Channel1 是唯一解

F1 系列里，外设触发哪个 DMA 通道是硬件连线写死的，不是可配置项。ADC1 的请求固定接在 DMA1_Channel1 上（ADC2 → 通道 2，ADC3 → 通道 5）。

所以这里不存在"选择"，只有"查表得到"。写代码前去参考手册的 DMA 请求映射表查一眼，比试出来快得多。

8 个半字取平均

ADC 单次读数天然带抖动（电源纹波、杜邦线天线效应）。缓冲区设 8 个半字，取平均后抖动明显变小，OLED 上的数字不会乱跳。

代价只有 RAM 里 16 字节 —— 换来的稳定度非常划算。这也是"循环模式"的另一个好处：不需要任何软件干预，平均值永远是最近 8 次采样的。

3.3 采样时间为什么调大：这是最容易忽略的一步

代码里写的是 ADC_SampleTime_55Cycles5，为什么不是默认的 1.5 周期？ 这不是凑数，是跟光敏分压电路的输出阻抗有关
▶

ADC 是怎么采样的：内部有一个采样电容 CADC（约 8 pF），采样阶段把它通过外部电路"充"到被测电压。这个过程需要时间，时间常数 τ = (R源 + RADC) × CADC。

光敏模块的输出级是一个 10 kΩ 电阻和光敏电阻分压，等效输出阻抗在几 kΩ 到十几 kΩ 量级 —— 比用运放缓冲的信号源高得多。源阻抗高 → 时间常数大 → 采样时间不够，电容还没充到目标值就被切走了，读出来的数偏低。

采样时间总转换周期12 MHz 下耗时对高阻抗信号源
1.5 周期14 周期1.17 µs明显欠采样，读数偏低且不稳定
13.5 周期26 周期2.17 µs勉强够用
55.5 周期68 周期5.67 µs充分建立，读数稳定
239.5 周期252 周期21 µs过于保守，转换速率降到 48 kHz
结论：55.5 周期。判据是 "源阻抗高 → 采样时间留足建立时间"。本项目最快只需要几百 Hz 的采样率，把 5.67 µs 花在精度上完全不亏。
顺手提一个硬件层面的坑 如果信号源阻抗特别高（> 50 kΩ），光靠延长采样时间也救不回来，正确做法是在分压点和 PA0 之间加一级电压跟随器（运放缓冲）。本模块的阻抗量级还没到那一步，55.5 周期够用。

3.4 ADC 时钟为什么是 12 MHz

ADC 模拟部分有硬性上限 ADCCLK ≤ 14 MHz（数据手册规定，超了精度会掉甚至不工作）。APB2 是 72 MHz，所以必须分频：

分频ADCCLK能否用
RCC_PCLK2_Div236 MHz超标，禁止
RCC_PCLK2_Div418 MHz仍超标
RCC_PCLK2_Div612 MHz本工程
RCC_PCLK2_Div89 MHz可用，但转换更慢，没必要

分频系数只有 2/4/6/8 四挡（RCC_ADCCLKConfig 能给的选项就这些），所以能选的最大合规值就是 12 MHz —— 在合规的前提下取最大，转换最快。

3.5 ADC 初始化的顺序不能乱

System/AD.c顺序是有讲究的，标了序号
void AD_Init(void)
{
    RCC_APB2PeriphClockCmd(RCC_APB2Periph_ADC1 | RCC_APB2Periph_GPIOA, ENABLE);
    RCC_ADCCLKConfig(RCC_PCLK2_Div6);   /* 72/6 = 12 MHz，上限 14 MHz */

    /* ① 模拟输入模式：GPIO_Mode_AIN。配成推挽/上拉都会破坏采样 */
    /*    原工程 Timer.c 把 PA0 配成上拉输入，AD.c 又配成模拟输入，两者打架 */
    GPIO_InitStructure.GPIO_Mode = GPIO_Mode_AIN;
    GPIO_InitStructure.GPIO_Pin  = GPIO_Pin_0;
    GPIO_Init(GPIOA, &GPIO_InitStructure);

    /* ② 先配 DMA，再开 ADC 的 DMA 请求与 ADC 本体 */
    DMA_AdcInit(s_adcBuffer, AD_BUFFER_SIZE);

    ADC_InitStructure.ADC_Mode               = ADC_Mode_Independent;   /* 单 ADC，不玩双 ADC 同步 */
    ADC_InitStructure.ADC_DataAlign          = ADC_DataAlign_Right;    /* 12 位右对齐 */
    ADC_InitStructure.ADC_ExternalTrigConv    = ADC_ExternalTrigConv_None;
    ADC_InitStructure.ADC_ContinuousConvMode  = ENABLE;   /* 连续转换，转完立刻转下一次 */
    ADC_InitStructure.ADC_ScanConvMode        = DISABLE;  /* 只有一路，不需要扫描 */
    ADC_InitStructure.ADC_NbrOfChannel        = 1;
    ADC_Init(ADC1, &ADC_InitStructure);

    /* ③ 规则通道序列第 1 位 = 通道 0，采样 55.5 周期 */
    ADC_RegularChannelConfig(ADC1, ADC_Channel_0, 1, ADC_SampleTime_55Cycles5);

    ADC_DMACmd(ADC1, ENABLE);
    ADC_Cmd(ADC1, ENABLE);

    /* ④ 校准：必须先复位校准、等标志，再启动校准、等标志 —— 顺序错会读到错误值 */
    ADC_ResetCalibration(ADC1);
    while (ADC_GetResetCalibrationStatus(ADC1) == SET);
    ADC_StartCalibration(ADC1);
    while (ADC_GetCalibrationStatus(ADC1) == SET);

    /* ⑤ 软件触发。因为开了连续模式，这一下就够它一直转下去 */
    ADC_SoftwareStartConvCmd(ADC1, ENABLE);
}
规则通道 vs 注入通道 ADC 有两组通道序列：规则组按顺序自动转换，注入组可以打断规则组、优先转换（像中断一样）。本工程只有一路信号、也不要求"紧急插播"，所以只用规则组。如果以后要加"过流保护"这种必须优先响应的采样，才需要考虑注入组。

4 · 串口 / OLED / 板载 LED 的选型外围器件的选择逻辑

4.1 为什么是 USART1（PA9 / PA10）

串口总线默认引脚本项目状态
USART1APB2（72 MHz）PA9 / PA10使用中
USART2APB1（36 MHz）PA2 / PA3空闲
USART3APB1PB10 / PB11PB11 按键预留

选 USART1 的实际理由：

  • PA9/PA10 不与任何已定外设冲突（PWM 在 PA1，ADC 在 PA0，SWD 在 PA13/PA14）
  • 挂 APB2 跑 72 MHz，波特率计算的分频余量更大，误差更小
  • 几乎所有 STM32 最小系统板的 USB-TTL 都是引到 PA9/PA10，接线说明最好找
USART2 其实也能用，甚至引脚（PA2/PA3）更空 但注意 TIM2 的 CH3/CH4 也在 PA2/PA3 —— 一旦以后想再增加一路 PWM 输出，USART2 就成了障碍。信息量就在这些细节里：选引脚时不只是看"现在谁占了"，还要看"谁将来可能要用"。留出 TIM2 的两个通道，等于给未来的电机/呼吸灯留了余地。

接收为什么要用中断 + 环形缓冲

如果主循环里"等一个字节 → 处理 → 再等下一个"，那么主循环被 OLED 刷新或渐变任务占住的那几毫秒里，PC 发来的字节就丢了。解决办法是让中断承担搬运、让主循环承担解析：

Hardware/Serial.c中断只搬字节，解析全在主循环
/* 中断服务函数：只做两件事 —— 取字节、存进环形缓冲。绝不在这里解析命令 */
void USART1_IRQHandler(void)
{
    if (USART_GetITStatus(USART1, USART_IT_RXNE) == SET)
    {
        Serial_RxPush((uint8_t)USART_ReceiveData(USART1));
        USART_ClearITPendingBit(USART1, USART_IT_RXNE);
    }

    /* 溢出错误必须读一次 DR 才能清除，否则中断会一直不停地进 */
    if (USART_GetFlagStatus(USART1, USART_FLAG_ORE) == SET)
    {
        (void)USART_ReceiveData(USART1);
    }
}

/* 主循环里把散字节拼成整行，拼好才返回 1 */
uint8_t Serial_Poll(void)
{
    uint8_t byte;
    while (Serial_RxPop(&byte))
    {
        if (byte == '\r') { continue; }        /* CRLF / LF 都能用 */
        if (byte == '\n')
        {
            if (s_lineLength > 0) { s_lineBuffer[s_lineLength] = '\0'; s_lineLength = 0; return 1; }
            continue;
        }
        if (s_lineLength < SERIAL_LINE_SIZE) { s_lineBuffer[s_lineLength++] = (char)byte; }
        else { s_lineLength = 0; }              /* 超长整行丢弃，防止缓冲溢出 */
    }
    return 0;
}
环形缓冲的判空/判满怎么写才不出错 保留一个空位：next = (head + 1) % SIZE，当 next == tail 时认定为满，静默丢字节而不是覆盖。这样做的好处是"满"和"空"两个状态不会混淆（如果允许写满，head == tail 就同时是满和空了，没法区分）。

协议为什么用 ASCII 行协议

对二进制协议来说，ASCII 明文协议的"体积效率"很差。但本项目选它的理由很实在：

  • 可以在串口助手里直接手敲调试，不需要写上位机
  • 出错时肉眼就能看出问题，不用拿十六进制对照表
  • 数据量极小（每 200 ms 约 40 字节），占用带宽可以忽略

如果以后要传波形数据（每秒几万点），那才需要换成二进制帧 + 校验和。

4.2 OLED 为什么用软件 I2C

PB6/PB7 恰好就是硬件 I2C1 的默认引脚 —— 所以这里本来就有一个选择：用硬件 I2C1，还是用 GPIO 模拟。

选了软件 I2C（GPIO 模拟）

  • STM32F1 的硬件 I2C 有历史遗留的卡死/总线锁死问题（errata 文档里有记录），调试时很难定位
  • 软件 I2C 的时序完全可控，出问题一眼能看出是哪一位
  • 换到别的单片机可以整段复制，不受外设差异影响

代价与注意点

  • 占用 CPU 时间（但 OLED 只 500 ms 刷一次，影响极小）
  • 必须配成开漏输出 GPIO_Mode_Out_OD，因为 I2C 总线是"线与"结构，多个设备共用一根线，只能靠上拉电阻拉高
  • 总线上需要上拉电阻（OLED 模块通常已自带 4.7 kΩ）
文档里曾经写错的一处 docs/hardware.md 最初把 PB6/PB7 记成了"推挽输出"，但代码里实际是 GPIO_Mode_Out_OD 开漏 —— 代码是对的，文档写错了。这类"文档与实践脱节"的问题在长期项目里很常见，所以那份文档开头特意写了一句：修改硬件连接后必须同步更新本文档与 README 的引脚表。

4.3 板载 LED 为什么用 PC13

需要一个"程序还活着"的指示，最省事的做法是用最小系统板上已经焊好的那颗 LED —— 它在 PC13，低电平点亮（阳极接 3V3，阴极接 PC13）。

关键在于它不占用任何本该给别的功能的引脚。原工程曾经把状态灯放在 PA1/PA2，结果和 PWM 正面撞车 —— 这就是"选型时忘了查占用表"的代价。另外注意 PC13 的驱动能力很弱（数据手册标注只能小电流），推挽输出直接驱动 LED 是可以的，但不能拿来驱动大负载。

5 · 分步实现时间线如果重来一次，我会按这个顺序写

顺序不是随便排的，遵循一条原则：每一步都必须能独立验证。写完不能立刻看到效果的东西，最后一定会变成"不知道哪里错"的一大坨。

阶段 0　需求翻译与资源规划

产出：一张手写的占用表 · 不写任何代码

把"光控灯"翻译成三路信号（模拟量、可调方波、串行数据），然后按第 1 节的四步法给每一路分配外设。这一步花 20 分钟，能省掉后面几小时的返工。

验证方法：把占用表拿给"假想的另一个模块"检查一遍 —— 每个引脚、每个外设都只能出现在一行里。

阶段 1　最小可运行骨架：时钟 + Delay + 串口

验证：串口能收到一行字

先建立"能跟外界说话"的能力。SystemInit() 把主频配到 72 MHz，Delay 提供微秒/毫秒级等待，串口能发字符串 —— 有这三样，之后所有模块的调试都有输出可看。

为什么排第一：串口是后面所有调试的眼睛。没有它，只能靠"灯亮不亮"猜，效率差一个数量级。

阶段 2　ADC + DMA 采集光敏

验证：串口打印的 ADC 值随遮挡变化

配 GPIOA-PA0 为模拟输入 → 配 DMA1_CH1 循环模式 → 配 ADC1 连续转换、55.5 周期采样 → 校准 → 软件触发。主循环里取平均值打印出来。

关键抉择：采样时间必须给足（3.3 节）；DMA 通道是硬件固定的，只能查表得到。

为什么排在 PWM 前面：先拿到"输入"，才能谈"输出多少"。总要先知道环境有多暗。

阶段 3　TIM2 PWM 驱动 LED

验证：串口发指令能把灯的亮度改掉

PA1 配复用推挽 → TIM2 时基 72 分频、ARR = 999 → 输出比较 CH2 用 PWM1 模式 → 先手动调 PWM_SetDuty() 试出灯的响应曲线。

最该先做的一件事：确认"LED 接法是拉电流还是灌电流"。接法反了会出现"占空比越大反而越暗"，这时候改极性比改接线省事（改 TIM_OCPolarity_High 为 Low）。

阶段 4　连接输入输出：映射函数

验证：遮光 → 灯亮

把 ADC 值映射成亮度百分比。用两个标定端点做线性插值，公式设计成对方向免疫 —— 不管"暗对应高 ADC"还是"暗对应低 ADC"，都不用改代码。

Hardware/LightSensor.c分子分母同号变化，方向自动适配
uint8_t LightSensor_ToDuty(uint16_t adc)
{
    int32_t denominator = (int32_t)LIGHT_ADC_DARK - (int32_t)LIGHT_ADC_BRIGHT;
    int32_t numerator   = ((int32_t)adc - (int32_t)LIGHT_ADC_BRIGHT) * 100;
    int32_t duty;

    if (denominator == 0) { return 0; }        /* 防除零：两个端点不能相等 */

    duty = numerator / denominator;              /* 负数会向零截断，所以下面必须钳位 */

    if (duty < 0)   { duty = 0; }
    if (duty > 100) { duty = 100; }
    return (uint8_t)duty;
}

为什么写成这样而不是 100 - x：如果以后换成"光照越强灯越亮"的场景，只要把两个端点宏对调就行，函数体一个字都不用改。

阶段 5　把渐变改成非阻塞状态机

验证：渐变过程中串口依然秒回

原来的写法是"设一个目标值，然后 delay_ms(10) 循环逼近"，带两个致命问题：阻塞（期间串口失联）和耦合（调光模块自己去调 PWM 初始化）。改法是把渐变拆成一次调用只走一小步的 CtLED_Update()，由主循环每 10 ms 调一次。

Hardware/CtLED.c一次调用 = 走一步 = 立刻返回
void CtLED_Update(void)
{
    if (s_currentDuty == s_targetDuty) { return; }   /* 已经到了，什么都不做 */

    if (s_currentDuty < s_targetDuty)
    {
        s_currentDuty += GRADIENT_STEP;                    /* 每 10 ms 走 2% */
        if (s_currentDuty > s_targetDuty) { s_currentDuty = s_targetDuty; }
    }
    else
    {
        if (s_currentDuty >= GRADIENT_STEP) { s_currentDuty -= GRADIENT_STEP; }
        else { s_currentDuty = 0; }
        if (s_currentDuty < s_targetDuty) { s_currentDuty = s_targetDuty; }
    }

    PWM_SetDuty(PWM_PERCENT_TO_DUTY(s_currentDuty));
}
注意 else 分支里那两个 if 无符号数递减时如果不加保护，0 - 2 会变成 65534，灯会瞬间爆亮。"向下走的时候要防下溢，向上走的时候要防上溢" —— 两边的钳位一个都不能省。

阶段 6　应用层状态机：AUTO / PC 双模式

验证：PC 模式下遮光，灯纹丝不动

把"谁来决定亮度"这个判断集中到一个地方。核心是：PC 模式下，光敏映射函数在代码路径上根本不会被调用。

User/App.c模式分支是"零调用"，不是"算了但不用"
void App_Process(void)
{
    /* 1. 串口命令优先级最高 */
    if (Serial_Poll()) { App_HandleCommand(Serial_GetLine()); }

    /* 2. 取最新的 ADC 平均值（DMA 在后台一直刷新缓冲） */
    s_adcValue = LightSensor_GetRaw();

    /* 3. 模式逻辑 —— 这里就是"PC 模式不受光照影响"的实现 */
    if (s_mode == APP_MODE_AUTO)
    {
        CtLED_SetTarget(LightSensor_ToDuty(s_adcValue));   /* 只有 AUTO 才会走这一行 */
    }
    else if ((Timer_GetTick() - s_lastCommandTick) > APP_PC_TIMEOUT_MS)
    {
        App_SetMode(APP_MODE_AUTO);                            /* 看门狗：3 秒没指令就交还控制权 */
        Serial_SendString("EVT,pc timeout\r\n");
    }

    /* 4~7. 渐变 / 上报 / 刷屏 / 心跳，各自按自己的周期触发 */
    if (Timer_IsElapsed(&s_lastGradient, APP_GRADIENT_PERIOD_MS)) { CtLED_Update(); }
    if (Timer_IsElapsed(&s_lastReport,   APP_REPORT_PERIOD_MS))   { App_SendStatus(); }
    if (Timer_IsElapsed(&s_lastDisplay,  APP_DISPLAY_PERIOD_MS))  { App_UpdateDisplay(); }
    if (Timer_IsElapsed(&s_lastLed,      APP_LED_PERIOD_MS))      { LED_Toggle(); }
}

设计要点：每个任务都是"查一下时间够不够 → 够就做一次 → 立刻返回"。没有任何一处 while 等待，所以任何一个任务出问题都不会把别的任务拖死。这就是所谓前后台架构：后台是中断和 DMA，前台是这个函数。

阶段 7　（未完成）按键手动调光

6 · 踩过的 7 个坑每一个都留下了"怎么发现的"记录

前 4 个是架构性错误（代码单独能编译通过，合起来必崩）；后 3 个是工具链问题（跟代码质量无关，但会白白耗掉一晚上）。

坑 1　TIM2 被两个模块同时初始化

症状

PWM 输出和系统时基只有一个能用，另一个完全失效；换初始化顺序，失效的模块也跟着换。

根因

Timer.c 用 TIM_TimeBaseInit(TIM2, …) 配时基，PWM.c 也用 TIM_TimeBaseInit(TIM2, …) 配 PWM。后者把前者的 ARR/PSC 全写掉；而 TIM_Cmd(TIM2, ENABLE) 谁最后调用谁说了算。

怎么发现的

把所有模块的源码放在一起 grep 一遍外设名，TIM2 出现了两次，出现在两个不同文件里。这类问题靠读单个文件永远发现不了。

修正

时基改用 TIM3，PWM 独占 TIM2。并在两个文件头部各写一行注释声明归属，防止以后有人再加一个"顺手用一下 TIM2"的模块。

坑 2　PA0 被配了两次，模式还不同

Timer.c 把 PA0 配上拉输入（当时想拿它当外部时钟输入引脚），AD.c 把 PA0 配成模拟输入。**后配的把先配的覆盖掉** —— 谁在后面取决于初始化的调用顺序，于是"ADC 读数不可信"这个现象时有时无，极难复现。

修正：PA0 只由 AD.c 负责，配成 GPIO_Mode_AIN。一个引脚只能有一个 owner，这是铁律。

坑 3　LED 模块抢走了 PWM 的引脚（这就是"灯一直亮"的真正原因）

症状

调光不起作用，灯只会亮或灭，不会渐亮渐暗。

表面解释 vs 真正原因

当时得到的解释是"人眼视觉暂留，1 kHz 太快看不出来" —— 这个解释听着有道理，但完全不是原因。真正的原因是 LED.c 把 PA1/PA2 配成了普通推挽输出，把定时器的复用功能覆盖掉了，PA1 上根本没有 PWM 波形，只剩 GPIO 电平。

怎么证伪的

看代码顺序：LED_Init() 里 GPIO_InitStructure.GPIO_Mode = GPIO_Mode_Out_PP，引脚号 GPIO_Pin_1 | GPIO_Pin_2。而 PWM.c 要的是 GPIO_Mode_AF_PP。同一个引脚，一个要普通输出、一个要复用输出 —— 必然打架。

修正

状态灯改到 PC13（板上自带），PA1 专职 PWM。教训：一个"听起来合理"的解释，如果不指向具体的代码行，大概率是错的。

坑 4　调光模块内部调 PWM 初始化 + 2 秒阻塞延时

原 CtLED.c 的 AD_LED() 函数里，第一步是调用 PWM_Init()，然后用 delay 循环 2 秒来"渐变"。

  • 层次倒置：器件层（CtLED）不应该去初始化驱动层（PWM）—— 那是 App_Init() 的职责。每调一次亮度就重配一遍定时器，纯属浪费且容易出错。
  • 阻塞 2 秒：这 2 秒里串口收不到任何东西、OLED 不刷新、看门狗不喂。用户看到的现象是"发指令后程序像死了一样"。

修正：PWM_Init() 只在 CtLED_Init() 里调一次；渐变改成 5 阶段里的非阻塞状态机。依赖方向永远是上层调下层，下层不回头调上层。

坑 5　下载报 No ULINK2/ME Device found

背景：Keil 把"用哪个下载器"存在 Project.uvoptx 里。这个文件属于本机配置，通常被 .gitignore 挡住不进仓库 —— 于是新克隆下来的工程没有这个文件，Keil 会重新生成一份，默认值就是 ULINK2/ME。

判据：对比原工程和副本的 uvoptx 文件，发现只有三处不同：

配置项能正常下载的工程报错的工程
<nTsel>50
<pMon>STLink\ST-LINKIII-KEIL_SWO.dllBIN\UL2CM3.DLL
驱动参数条目有 ST-Link 条目整段缺失

修正：在 Keil 里 Options for Target → Debug 下拉框改成 ST-Link Debugger，Settings 里 Port 选 SW，确定保存。改完记得点「确定」而不是「取消」 —— 点取消所有改动都不保存，这是最容易反复栽的地方。

坑 6　编译报 #error: Please select first the target STM32F10x device

根因：工程的宏定义里只有 USE_STDPERIPH_DRIVER，缺 STM32F10X_MD。Start/stm32f10x.h 靠这个宏来判断芯片容量等级（小容量/中容量/大容量/互联型），没定义就直接 #error 中断编译。

为什么原来没暴露：原工程的 stm32f10x.h 里那行 #define STM32F10X_MD 是注释状态，一直靠"某些文件里恰好包含顺序不对"侥幸没触发。一旦真正全量编译就暴露了。

修正：Options for Target → C/C++ → Define 填 USE_STDPERIPH_DRIVER,STM32F10X_MD（英文逗号）。

这个坑的价值：提早用命令行编译验证 与其在 Keil 里点了编译再等报错，不如直接用 Keil 自带的 armcc 命令行把工程编一遍 —— 几秒钟就能把这类"配置缺失"的问题全抓出来，再打开 IDE 时就知道能过。

坑 7　Keil 开着的时候改工程文件，保存后被覆盖

现象：已经改好的 Project.uvprojx（补了 STM32F10X_MD）和 Project.uvoptx（改了下载器），过一会儿再看，全变回旧值了。

判据：看文件修改时间戳 —— 我的修改是 22:5x，而文件时间显示 23:15，整点被改写。

根因：Keil 把工程配置缓存在内存里。只要你在界面上动过任何设置（打开 Options 再确定、或者按 F7 触发自动保存），它就按内存里的旧状态整体重写磁盘文件，你之前的外部修改全部作废。

结论（通用规则）：只要涉及 IDE 会管理的配置文件，必须先让 IDE 完全退出，改完再重新打开；或者干脆全部在 IDE 界面里改。

7 · 参数是怎么算的动手调一调，看数字怎么变

项目里所有"看起来像魔法数字"的常量，背后都是一两步乘除。下面两个计算器可以改参数实时算 —— 试着故意填错，看看会撞上哪条约束。

7.1 PWM 频率与分辨率

试试这几个值 · PSC=71, ARR=999 → 1 kHz / 1000 级（本项目）
· PSC=7, ARR=999 → 10 kHz / 1000 级（更快，但没意义）
· PSC=71, ARR=99 → 10 kHz / 100 级（暗部会跳变）
· PSC=71, ARR=9999 → 100 Hz，肉眼可见闪烁
· PSC=0, ARR=999 → 72 kHz，依然能出波形，但分辨率没变化，白费

7.2 ADC 转换时间与采样率

试试把分频改成 Div2 或 Div4 你会看到 ADCCLK 超过 14 MHz —— 这是芯片规定的硬上限，超了精度不受保证。这就是为什么代码里只能选 Div6（12 MHz）或 Div8（9 MHz）。

8 · 自测点一下选项就知道对错

1. 光敏信号为什么走 PA0（ADC1_IN0），而不是同样空闲的 PA2？
因为 PA0 的采样精度比 PA2 高
因为 PA0 与已占用资源不冲突，且通道号与引脚序号对齐、无需重映射
因为 PA2 被串口占用了
ADC 各通道的电气特性完全相同，不存在"精度更高"的说法。选 PA0 的理由是约束最少：PA1 已给 PWM，PA9/10 给了串口，PA13/14 是调试口；而 PA0 恰好就是通道 0，配置时不容易写错。PA2 其实是空闲的（它的"被占"是 TIM2_CH3 的复用，本项目没用）。
2. 采样时间从 1.5 周期改成 55.5 周期，主要解决了什么问题？
光敏分压电路输出阻抗较高，需要更长的时间给采样电容建立电压
提高 ADC 的分辨率，从 10 位变成 12 位
降低 ADC 时钟，避免超过 14 MHz 上限
分辨率由硬件固定为 12 位，跟采样时间无关；ADC 时钟是由 RCC_ADCCLKConfig 决定的，也是另一件事。采样时间只影响"采样电容能不能被充满" —— 源阻抗高就必须给足时间，否则读数偏低且不稳定。
3. 为什么 ADC1 必须用 DMA1_Channel1？
因为通道 1 优先级最高，采样最快
因为其他通道都被占用了
因为 F1 系列里外设与 DMA 通道的对应是硬件固定的，ADC1 只能接通道 1
这不是"选择"，是查表得到的硬连线。参考手册的 DMA 请求映射表规定：ADC1 → DMA1_CH1，ADC2 → DMA1_CH2，ADC3 → DMA1_CH5。项目里所有 DMA 通道都没被占用，唯一的原因就是硬件决定了只能这么接。
4. 系统节拍为什么用 TIM3 而不是更省事的 SysTick？
SysTick 是 24 位，计不到 1 ms
SysTick 已经被标准库的延时函数占用，共用会导致时延基准被反复改写，且它的中断优先级最低
TIM3 的精度比 SysTick 高得多
SysTick 做 1 ms 中断完全没问题（24 位绰绰有余）。问题在资源归属：Delay.c 已经在用它了，两个模块抢同一个内核定时器，谁后初始化谁说了算。用空闲的 TIM3 做节拍，两边彻底隔离。
5. 原工程"灯一直亮、调不暗"的真正原因是什么？
人眼视觉暂留，1 kHz 太快看不出来
LED 的限流电阻选小了
LED 模块把 PA1/PA2 配成了普通推挽输出，覆盖掉定时器的复用功能，PA1 上根本没有 PWM 波形
"视觉暂留"这个解释听起来专业，但它不指向任何一行可以修改的代码，所以是错的。LED.c 里的 GPIO_Mode_Out_PP 与 PWM.c 需要的 GPIO_Mode_AF_PP 在同一个引脚上互斥 —— 这才是根因，改法是状态灯挪到 PC13。
6. 新克隆的工程一点下载就报 No ULINK2/ME Device found，为什么？
ST-Link 驱动没装
存放下载器设置的 .uvoptx 属于本机配置、不在仓库里，Keil 重新生成时默认选了 ULINK2/ME
芯片坏了
判据很直接：能正常下载的原工程和报错的新工程，uvoptx 里只有下载器相关的三处不同（nTsel、pMon、驱动参数条目）。如果是驱动没装，那"Debug 下拉框里根本不会出现 ST-Link Debugger 这一项"—— 但它是存在的。
